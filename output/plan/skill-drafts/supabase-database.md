# Supabase Database Conventions

## Quick start / rules

### Migration workflow

- Migration files live in `supabase/migrations/`.
- Naming: `supabase migration new <description>` generates `<timestamp>_<description>.sql`.
- One migration per logical change group (one table + its indexes + triggers, or one feature's tables).
- Never modify a migration applied to any shared environment (local dev, staging, production).
- Seed data goes in `supabase/seed.sql`, never in migrations.
- Run `supabase db reset` to re-apply migrations + seed locally.
- Schema-only: `migration new`. To pull remote changes: `supabase db pull`.

### Table and column naming

- Tables: plural, snake_case (`clients`, `appointment_items`).
- Columns: snake_case, no table prefix (`name`, not `client_name`).
- Primary keys: `id uuid PRIMARY KEY DEFAULT gen_random_uuid()`.
- Foreign keys: `{entity}_id uuid REFERENCES {entity}s(id)`.
- Junction tables: `{entity1}_{entity2}` (`staff_branch_assignments`).

### Required columns for every tenant-scoped table

Every table that holds tenant data MUST include:
- `tenant_id uuid NOT NULL REFERENCES tenants(id)` — the tenant isolation key.
- `created_at timestamptz NOT NULL DEFAULT now()`.
- `updated_at timestamptz NOT NULL DEFAULT now()`.

Branch-scoped tables also include `branch_id uuid REFERENCES branches(id)`.

Business-mutation tables (where you need to track who did what) also include:
- `created_by uuid REFERENCES auth.users(id)`.
- `updated_by uuid REFERENCES auth.users(id)`.

### Money columns

Always `numeric(12,3)`, never `float`, `double precision`, or `integer`.
KWD uses 3 decimal places; `numeric` avoids floating-point rounding errors.

### Time zones

Always `timestamptz`, never `timestamp without time zone`.
Store IANA timezone names (e.g. 'Asia/Kuwait') in the branch record, not offsets.
Application layer converts UTC to local time for display.

### Soft delete

- Core entities (clients, services, staff, branches): `is_active boolean` or `is_deleted boolean`.
- Appointments: status-based (cancelled, no_show). Never hard-delete.
- Sales: status-based (voided). Financial records are immutable.
- Always include the soft-delete column in RLS policies: `AND is_deleted = false`.
- Indexes on `(tenant_id, is_deleted)` for soft-delete filtered queries.

### ID strategy

All primary keys: `uuid DEFAULT gen_random_uuid()`.
Human-readable reference numbers (sale_number, appointment ref_number) are generated by the application layer using a sequence table.

### Optimistic concurrency

Use `updated_at` for optimistic locking:
```sql
UPDATE {table} SET ... WHERE id = $1 AND updated_at = $2;
```
If zero rows affected, the row was modified by another request — retry or reject.

### updated_at trigger

Every table with `updated_at` needs this trigger:
```sql
CREATE OR REPLACE FUNCTION public.set_updated_at()
RETURNS trigger LANGUAGE plpgsql AS $$
BEGIN
  NEW.updated_at = now();
  RETURN NEW;
END;
$$;

CREATE TRIGGER set_updated_at_{table}
  BEFORE UPDATE ON public.{table}
  FOR EACH ROW EXECUTE FUNCTION public.set_updated_at();
```

## RLS policy templates

### Tenant isolation helper functions

These live in `000004_create_memberships.sql`:

```sql
-- Returns tenant_ids the current user belongs to
CREATE OR REPLACE FUNCTION public.get_user_tenant_ids()
RETURNS SETOF uuid
LANGUAGE sql STABLE SECURITY DEFINER
SET search_path = public
AS $$
  SELECT tenant_id FROM public.memberships
  WHERE user_id = (SELECT auth.uid()) AND is_active = true;
$$;

-- Check if user has a specific role in a tenant
CREATE OR REPLACE FUNCTION public.has_tenant_role(p_tenant_id uuid, VARIADIC p_roles text[])
RETURNS boolean
LANGUAGE sql STABLE SECURITY DEFINER
SET search_path = public
AS $$
  SELECT EXISTS (
    SELECT 1 FROM public.memberships
    WHERE user_id = (SELECT auth.uid())
    AND tenant_id = p_tenant_id
    AND role = ANY(p_roles)
    AND is_active = true
  );
$$;
```

Key points:
- `SECURITY DEFINER` — runs as function owner, bypasses RLS on `memberships` itself.
- `STABLE` — Postgres caches the result per statement, not per row.
- `(SELECT auth.uid())` — scalar subquery, evaluated once (InitPlan), not per row.
- `SET search_path = public` — prevents search_path injection attacks.
- `GRANT EXECUTE` to `authenticated`, never to `anon`.

### Standard tenant isolation policy (per-table pattern)

```sql
ALTER TABLE public.{table} ENABLE ROW LEVEL SECURITY;

-- SELECT: user must belong to the row's tenant
CREATE POLICY "{table}_select" ON public.{table}
  FOR SELECT TO authenticated
  USING (tenant_id IN (SELECT public.get_user_tenant_ids()));

-- INSERT: user must belong to the tenant being written to
CREATE POLICY "{table}_insert" ON public.{table}
  FOR INSERT TO authenticated
  WITH CHECK (tenant_id IN (SELECT public.get_user_tenant_ids()));

-- UPDATE: same as SELECT + tenant ownership
CREATE POLICY "{table}_update" ON public.{table}
  FOR UPDATE TO authenticated
  USING (tenant_id IN (SELECT public.get_user_tenant_ids()))
  WITH CHECK (tenant_id IN (SELECT public.get_user_tenant_ids()));

-- DELETE: same as SELECT
CREATE POLICY "{table}_delete" ON public.{table}
  FOR DELETE TO authenticated
  USING (tenant_id IN (SELECT public.get_user_tenant_ids()));
```

### Role-gated policy (managers/owners only)

For operations restricted by role:
```sql
CREATE POLICY "{table}_insert" ON public.{table}
  FOR INSERT TO authenticated
  WITH CHECK (public.has_tenant_role(tenant_id, 'tenant_owner', 'branch_manager'));
```

### Never do these

- `USING (true)` — defeats RLS entirely.
- Service role key in client-side code or environment variables exposed to the browser.
- Missing `WITH CHECK` on INSERT/UPDATE policies — tenant boundary becomes read-only, writes can forge data.
- RLS policy without `TO authenticated` — evaluated for anon users unnecessarily.
- Bare `auth.uid()` in subquery — use `(SELECT auth.uid())` for performance.

## How to add a new tenant-scoped table

Step-by-step:

1. Create migration: `supabase migration new create_<table_name>`.
2. Write CREATE TABLE with `id uuid PK`, `tenant_id uuid NOT NULL FK`, required columns.
3. Add indexes on `(tenant_id)` and any FK columns.
4. Add `updated_at` trigger.
5. Enable RLS and add the standard 4 policies (SELECT, INSERT, UPDATE, DELETE).
6. If the table contains branch-scoped data, add `branch_id uuid FK` and include the branch scope check in RLS.
7. Add `created_by`/`updated_by` if tracking who changed what.
8. Run `supabase db reset` locally to validate the migration.
9. Generate new types: `supabase gen types typescript --local > src/types/database.ts`.

## Constraint patterns

### Double-booking prevention

Use a trigger (not an exclusion constraint) for staff/resource conflict checking, because the time range lives on the parent `appointments` table. The trigger joins `appointment_items` to `appointments` and checks for overlapping `tstzrange` rows.

Error code: `23P01` (exclusion_violation). Application catches this and translates to "This time slot is no longer available."

### Money amounts

Always `CHECK (>= 0)`. Use `numeric(12,3)`.

### Date/time ordering

Always `CHECK (ends_at > starts_at)` or `CHECK (scheduled_end > scheduled_start)`.

### Soft-delete partial unique indexes

For tables with soft delete where uniqueness should ignore deleted rows:
```sql
CREATE UNIQUE INDEX idx_clients_tenant_email_unique
  ON public.clients(tenant_id, email)
  WHERE email IS NOT NULL AND is_deleted = false;
```

### Invoice numbering

Use `invoice_sequences` table with `next_number`. Application atomically increments:
```sql
UPDATE public.invoice_sequences
SET next_number = next_number + 1
WHERE branch_id = $1
RETURNING next_number - 1;
```

## Testing RLS

### Strategy

- Every policy must have a pgTAP test.
- Tests run in CI on every migration via `supabase test db` or `pg_prove`.
- Minimum coverage: per table, per operation, per role, plus cross-tenant and anon tests.

### Helper: rlsautotest

https://github.com/unitautogen/rlsautotest auto-generates pgTAP tests from RLS policies.

```bash
pip install rlsautotest
rlsautotest --db-url "$DATABASE_URL" --schema public --emit supabase/
```

### Manual pgTAP test pattern

```sql
-- supabase/tests/rls_clients.sql
BEGIN;
SELECT plan(3);

-- Simulate authenticated user from tenant A
SET LOCAL ROLE authenticated;
PERFORM set_config('request.jwt.claim.sub', 'USER-A-UUID', true);

-- Test: can see own tenant's clients
SELECT results_eq(
  'SELECT count(*) FROM clients WHERE tenant_id = ''TENANT-A-UUID''',
  ARRAY[5],
  'Tenant A user sees their 5 clients'
);

-- Test: cannot see other tenant's clients
SELECT is_empty(
  'SELECT * FROM clients WHERE tenant_id = ''TENANT-B-UUID''',
  'Tenant A user sees no clients from Tenant B'
);

-- Test: anon user sees nothing
SET LOCAL ROLE anon;
SELECT is_empty(
  'SELECT * FROM clients',
  'Anon user sees no clients'
);

ROLLBACK;
```

Write seed data in `supabase/seed.sql`. Seed data is only for local development and testing.

```sql

  ('00000000-0000-0000-0000-000000000011', '00000000-0000-0000-0000-000000000001', 'SpaCorner Kuwait City', 'Asia/Kuwait');
```

## Generated TypeScript types

After every migration change, regenerate types:

```bash
supabase gen types typescript --local > src/types/database.ts
```

The generated `Database` type provides full type safety for:
- `public.Tables` — table row shapes.
- `public.Enums` — generated from CHECK constraints.
- `public.Functions` — typed RPC arguments and returns.

Use throughout the codebase:
```typescript
import type { Database } from '@/types/database';

type Client = Database['public']['Tables']['clients']['Row'];
type ClientInsert = Database['public']['Tables']['clients']['Insert'];
```
