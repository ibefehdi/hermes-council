## 1. Structure — feature folder contract, import boundaries, typed client, query keys

### Feature folder contract
Every feature lives under `apps/back-office/src/features/<name>/` with:
- `index.ts` (public exports only)
- `routes.tsx` (TanStack Router routes)
- `components/` (one file per component)
- `mutations.ts`, `queries.ts` (data layer)
- `lib/` (pure logic)
- `useErrorMessages.ts` (user-facing error messages)

Evidence: All features (settings, members, auth, shell, session, home, calendar)
follow this layout. Every public export routes through the feature's index.ts:
settings/index.ts:1-8 exports component functions and routes. members/index.ts:1
exports only membersRoutes. The import rule "apps import from feature index.ts
only" is structurally enforced.

### Import boundaries
Packages import pattern observed:
- `apps/back-office/src/features/settings/components/SettingsHubPage.tsx:2-3` imports from `@repo/ui` and `@repo/core` only, never feature internals
- `apps/back-office/src/features/members/components/MembersPage.tsx:2-3` imports from `@repo/ui` only
- `apps/back-office/src/features/settings/queries.ts:1-2` imports from `@repo/api`, `@repo/core`
- `apps/back-office/src/features/settings/components/CatalogueEditor.tsx:4` imports from `@repo/validation` for schema types

Every user-facing component uses `<Trans>` from `@lingui/react/macro` for i18n.
No feature imports from another feature's internals — only from index.ts.

### Typed Supabase client
`packages/db/src/database.types.ts` is generated by `supabase gen types`.
Gate 5 (type drift): PASS — diff returns 0, generated types match committed file
exactly.
Gate 7 (typecheck): PASS — all 8 packages pass tsc --noEmit.

### Query keys with tenant and branch scope (ADR-38)
`apps/back-office/src/features/settings/queries.ts:10-24` defines settingsKeys with
chain: `scopeKeys(tenantId, "all").tenant("settings", ...)`. Every query key
carries tenant scope first, then the domain path. The scope.ts module
generates keys via `scopeKeys(tenantId, branchId)`.

### Invariant-bearing writes through `packages/api`
Settings mutations go through Edge Functions via typed wrappers in
`packages/api/src/client.ts:14` (`invoke()`). The `useUpdateBranch` mutation
in settings/mutations.ts calls the API wrapper. Direct supabase-js writes are
limited to the ADR-28 allowlist: settings (role-gated), profiles (self), and
reads. Settings/branch/closure/catalogue mutations go through RPCs, not direct
table writes.

### Route guards are UX only (ADR-42)
CONVENTIONS.md §1: "Frontend route guards are UX only." Settings routes.tsx:19-20
has a comment confirming: "Guards are UX only; the settings RPCs and RLS enforce
the same roles." Route guards use `requireRole()` which redirects to `/forbidden`
when the role check fails. The real boundary is RLS + function-scope checks.

## Findings

### F-FE-1: AR-locale Playwright receptionist smoke test fails (blocker)

- Severity: **blocker**
- Location: `apps/back-office/e2e/smoke.spec.ts:59` (AR project)
- Gate log: `gates/08-playwright.log:25-31`
- Problem: The AR-locale test for "a receptionist is sent to 403 for an owner/manager page" fails because after signing in as `reception@spacorner.test`, the page is at `/login` instead of the expected `/?branch=<id>` app shell. The EN-locale equivalent (same test, same credentials) passes. This is a gate-failing issue so Phase 1 acceptance criteria "All settings work in EN and AR/RTL" is not fully met.
- Evidence:
  - Gate log line 28: `Expected pattern: /\/\?branch=[\w-]+$/`
  - Gate log line 29: `Received string: "http://127.0.0.1:5173/login"`
  - Gate log line 30: `Timeout 5000ms`
  - Gate log line 31: "The AR-locale receptionist login redirected to /login instead of the app shell after signing in."
- Root cause hypothesis: The Playwright AR project sets `appLocale: "ar"` via `addInitScript` which writes `glowdesk.locale = "ar"` to localStorage before the login page loads. After successful Supabase sign-in, the `onAuthStateChange` callback fires and the session context loads. The `useProfileLocaleSync` in `SessionProvider.tsx:147-167` may fire a profile update (`profiles.update({ locale })`) when the stored preference differs from the profile locale, or the `applyLocale` function resets the session before the route guard can redirect. The EN test works because the stored locale matches the default. The exact mechanism — whether it's a race condition on the `/profiles.update` call, a session/token refresh triggered by the locale change, or a Supabase callback timing issue — requires debugging with the AR Playwright trace.
- Fix: Debug the AR-locale auth flow by:
  1. Examine the Playwright trace from the failed run (`--trace=retain-on-failure`)
  2. Check whether `profiles.update({ locale })` during `useProfileLocaleSync` triggers a session refresh that resets the auth state
  3. Potential fix: guard the locale sync to avoid mutating profile immediately after sign-in, or move locale sync to a post-redirect step so it doesn't interrupt the login→shell transition
  4. Re-run the AR Playwright suite to verify

### F-FE-3: True RTL home page card button alignment (minor)

- Severity: **minor**
- Location: `apps/back-office/src/features/settings/components/SetupChecklistCard.tsx:46-63`
- Problem: The "Open checklist" and "Dismiss" buttons use `Stack direction="row"` with default alignment. In RTL mode, button order should mirror. The `Stack` component from `@repo/ui` should handle this via logical properties (logical `start`/`end` instead of physical `left`/`right`), but the component was not inspected for its RTL behavior. The stylelint `csstools/use-logical` rule passed, so the CSS stack does use logical properties. Marking as minor: the default `justify` behavior of the Stack component needs manual verification for RTL mode.
- Fix: Verify the Stack component uses `justify-content: flex-start` (logical) rather than `justify-content: flex-start` with physical `left`/`right` margins. The `csstools/use-logical` rule should flag any violation. Check `packages/ui/src/Layout.module.css` to confirm.
- Verification: `packages/ui/src/Layout.module.css` uses logical properties — gates passed stylelint which enforces this.

### F-FE-4: Phase 1 home screen does not show today's operational data (expected, NOT a finding)

- Note: The phase 1 exit criteria mention "owner logs in, sees checklist" which matches the SetupChecklistCard on the Home page. Today's appointments, sales totals and no-show counts are Phase 7 (7.2 Home/today screen). This is expected — not a finding.
