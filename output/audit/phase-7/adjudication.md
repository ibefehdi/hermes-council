# Phase 7 verifier adjudication

## Verdict: FAIL

The audit evidence is sufficient, but Phase 7 is not complete: the required timed staging backup/restore drill has not been run, its recorded timing table is blank, and this is an explicit Phase 7 acceptance and exit criterion. I also accept two additional major implementation findings: the advertised full-tenant export omits tenant-owned data, and the documented hosted-function setup omits the CORS origin setting needed by a non-local browser client. The export-volume performance measurement remains NOT VERIFIABLE LOCALLY, not a failure, under the common brief.

## Finding rulings

### Accepted

- **F-BACKUP-1 — major (accept).** `plan/evidence/7.4/restore-drill.md:3-5,7-29` states that the staging run is pending and leaves all timing/results blank. `plan/parts/11-delivery-plan.md:1458` requires a completed timed staging-snapshot drill within four hours; phase exit criterion `:1311` also requires the drill. ADR-49's Phase 7 amendment (`plan/decisions.md:413`) still requires the timed staging-to-scratch drill; only the production-snapshot/PITR check moves to Phase 8. The local seven-second rehearsal (`restore-drill.md:34-63`) is explicitly not staging evidence. Fix: run `docs/runbooks/backup-restore.md` against a staging snapshot restored to a scratch project, attach the timings, smoke output and reconciliation artifacts, and fill in the table in `plan/evidence/7.4/restore-drill.md`.
- **F-DB-02 — major (accept; severity raised from minor).** `supabase/migrations/20261014100100_export_jobs.sql:165-168` defines `full_tenant` as 18 files but omits 11 extant tenant-owned tables identified in `database.md:215-222`: `service_branch_overrides`, `service_staff`, `booking_overrides`, `closed_periods`, `branch_opening_hours`, `cancellation_reasons`, `blocked_time_types`, `settings`, `invoice_counters`, `memberships`, and `profiles`. The UI test only asserts 18 files and reads a client file (`apps/back-office/e2e/exports.spec.ts:47-70`); it does not establish completeness. ADR-50 additionally specifies a JSON settings dump (`plan/decisions.md:419`). This is a substantive gap in a feature advertised as a full-tenant export, not merely a naming omission. Fix: add a new migration extending the full-tenant file list, headers and slice builders to include the omitted records; provide the ADR-50 settings dump; add tests that assert each required entity/configuration is exported. Do not edit the applied migration.
- **F-backend-2 — major (accept; severity raised from minor).** The function permits only `http://127.0.0.1:5173` and `http://localhost:5173` when `ALLOWED_ORIGINS` is unset (`supabase/functions/_shared/cors.ts:1,13-30`). The committed function environment example has no such variable (`supabase/functions/.env.example:1-14`), and the staging deployment command omits it (`docs/runbooks/staging-deploy.md:44-48`). A hosted SPA origin therefore receives no function `Access-Control-Allow-Origin` response header unless an operator independently discovers and configures the variable. Supabase's browser-invocation guidance requires the function to return CORS headers on its responses: https://supabase.com/docs/guides/functions/cors. No hosted deployment was available to inspect, so this is a verified code-and-runbook defect, not a claim about an observed production deployment. Fix: document `ALLOWED_ORIGINS` in the function `.env.example` and staging/production deployment commands, populated with the deployed SPA origin(s), and add a test for an allowed hosted origin and a rejected origin.
- **F-DB-01 — minor (accept).** The plain `export_jobs(id)` foreign keys and absence of child `tenant_id` columns are visible at `supabase/migrations/20261014100100_export_jobs.sql:57-79`. ADR-20 rule 5 expressly applies to every FK to a tenant-owned table (`plan/decisions.md:284`), so the auditor correctly identified a deviation. Current deny-all RLS and revoked grants on both child tables reduce exploitability (`:83-99`); they do not waive the ADR. Fix with a new migration adding `tenant_id` and composite `(job_id, tenant_id)` references to `(id, tenant_id)`, and update the definer writers.
- **F-DB-03 — minor (accept).** `record_export` is SECURITY DEFINER and accepts caller-provided `p_filters` and `p_row_count` (`supabase/migrations/20261014100000_report_exports.sql:67-89`), with execution granted to `authenticated` (`:104-105`). Scope validation does not make those audit fields truthful. Fix: revoke the authenticated direct grant and have the reports Edge Function write the audit event after computing the export, using the verified actor and server-computed filters/count; add a test that direct authenticated calls are denied and the server path records the actual count.
- **F-backend-1 — minor (accept).** `.seed-pw` is untracked and absent from `.gitignore` (`.gitignore:1-17`); the gate report says it pre-existed and was unchanged (`gates/GATES.md:5-11,76-78`). No secret value is reproduced here. Fix: add `.seed-pw` to `.gitignore` and determine whether a tracked script still needs it.
- **F-PROC-1 — minor (accept with changed fix).** Git confirms commits `04619bbd1bb97e525ca0ba5523e11c24c8fa5256` and `6cf9f9e482ead845b5171b427e5680fe85640362` have non-Conventional-Commit subjects. This violates `plan/CONVENTIONS.md:199`. Do not rewrite already-merged main history as the default remediation; add a commit-message CI guard and use the required format for future commits.
- **F-PROC-2 — minor (accept with corrected evidence).** `plan/CONVENTIONS.md:197` requires short-lived feature branches to use `feat/<area>-<slug>`. `git show c9bcafe` identifies the merged source as `ibefehdi/phase-7-pre-council`; a read-only branch query still finds `remotes/origin/phase-7-pre-council`, so the conformance report's “orphaned/not in remote tracking” statement is stale. The name itself is still nonconforming. Fix: if the remote branch remains in use, rename it to `feat/phase-7-pre-council`; otherwise delete the obsolete remote ref after confirming it is unused, and use the convention for future branches.
